# Digital Packaged Pattern Provider

The Digital Packaged Pattern Provider dispatches AE2 processing orders to real third-party machines. It checks recipe identity, links, machine structure, inventory, and energy before accepting the full input. The native machine performs the work, then the provider collects the result and actual returns.

## Connecting a machine

The standalone packaged provider discovers adjacent targets only. Enable the side facing the machine, and keep cables, chests, and air from separating the two blocks. Build native pedestals, injectors, light paths, mana, and energy infrastructure around the machine as required by its Mod.

An Adaptive Pattern Provider can hold a packaged provider in its slot. Use the [Distribution Connector](6.19_data_distribution_connector.md) by sneak-right-clicking the full Adaptive Pattern Provider block and then right-clicking the target machine. Remote links still require the same dimension and loaded chunks.

## Patterns and admission

- Patterns need the correct recipe category and exact recipe ID. Transfer a recipe from JEI or EMI before encoding.
- Editing inputs or outputs keeps the original recipe ID. Transfer the new recipe when switching recipes, and re-encode patterns written with the old matching format.
- Encode one recipe round. Only machines with a declared safe batch entry combine multiple rounds.
- Buckets, containers, catalysts, tools, and retained inputs follow the input and return rules on their integration pages.
- Output slots can use exact, ID, or recipe-declared Tag matching. Amounts must still be correct.

Before admission, the target machine and claimed components normally need to be empty and idle. The machine must select the recipe recorded by the pattern, and native structure and energy conditions must be met. A rejected preflight leaves materials in the CPU. After acceptance, the operation owns its inputs, machine, and shared components. Do not let players, pipes, or other tasks move them concurrently.

## Batching and reusable inputs

Batch limits change with energy, machine slots, output space, and native progress. One task owns a machine at a time, and a task may contain several logical rounds. Each integration page documents its supported machines and limits.

The Data Core or Trinity CPU borrows a set of reusable catalysts for each machine it runs concurrently. Only consumables scale with the number of rounds. The session holds the catalysts between rounds and returns them when the batch ends or reaches a safe cancellation point. List session-managed catalysts only as inputs.

## Recovery and troubleshooting

Unloaded chunks pause operations. Replacing a machine or claimed structure part starts recovery of assets still held by the task.

Breaking a provider that holds an operation or returns can drop a single-use recovery receipt. Place the same type of provider at the original position in the same dimension, clear its return inventory, and use the receipt. Returns that cannot fit remain with the task until space becomes available.

| Symptom | First checks |
| --- | --- |
| CPU has inputs but the provider does not accept | Recipe category and ID, provider state, target link, structure, inventory, and quantity |
| Provider accepted but the machine has no inputs | Target face, input mode, target ownership, slot capacity, and loaded chunks |
| Machine has inputs but does not start | Energy, mana, aura, native structure, recipe selection, and run switch |
| Result stays in the machine | Output quantity and components, native returns, and provider online state |
| Result reaches the return inventory but the CPU is still waiting | ME storage space, the item key the CPU expects, and the pattern's output matching mode |
| First round finishes and the next stalls | Leftover inputs, output space, energy, and structure changes |
