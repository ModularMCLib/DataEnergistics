# Data Distribution Tower

The Data Distribution Tower takes over controllerless AE subnets through virtual allocation and equalizes FE endpoints by capacity fill ratio. It does not create a physical `IGridConnection` or merge the target Grid into the primary Grid.

## Placement and startup

Leave **3 continuous blocks** of vertical clearance above the tower base. The base must be connected to an ME network before the tower can work. The tower is an ordinary `REQUIRE_CHANNEL` device and consumes one real channel; virtual devices taken over by the tower are not directly limited by the upstream cable's 8/32-channel cap.

- Bare-hand right-click the tower body to open its control interface.
- Sneak bare-hand right-click to toggle the range display.
- The tower never force-loads target chunks. An unloaded target becomes unavailable and becomes usable again when the chunk returns.

## Connection modes

### Point-to-point

Point-to-point mode takes over only anchors selected through the [Distribution Connector](6.19_data_distribution_connector.md). Bindings remain persistent when the range is reduced later. Use the connector page for host selection, target faces, and unlinking.

### Range connection

Range mode continuously discovers disconnected single-node Grids in range. Multi-node, physically wired, or bridge-forming targets are reported as conflicts and are not taken over.

## Target types

- **AE only**: process devices with an available AE node;
- **FE only**: process devices that can input or output FE;
- **AE and FE**: enable both capabilities.

Point mode resolves the AE capability on all six anchor faces and de-duplicates node identities. One anchor may expose several subnets. Controller grids, grids owned by another primary, and bridge cycles are skipped, so one bind can partially succeed.

Only the anchor must share the tower dimension and be inside the bind range. Members of an accepted subnet may be out of range or in another dimension, but their chunks still need to be available.

## Channels and leases

The subordinate subnet keeps its own Pathing service while other Grid services delegate to the primary. Each `REQUIRE_CHANNEL` node requests one virtual lease; channel-free nodes cost nothing. A node without a lease stays offline without preventing sibling nodes from coming online.

Virtual capacity follows the target Controller situation:

- A Controller grid reported as a conflict supplies no virtual capacity.
- A controllerless primary supplies `32 × ChannelMode`.
- Every native Controller contributes all six faces, including faces adjacent to another Controller.
- A positive per-face capacity published by a Controller replaces the native 32-channel fallback.
- A Controller that publishes an authoritative total uses that total directly.
- Infinite mode has no finite capacity limit.

Native AE2 Pathing allocates physical channels first. Available virtual capacity is total capacity minus physical usage. Manual bindings are allocated before automatic bindings; equal-priority requests are granted FIFO, and capacity reduction revokes leases in reverse order.

## FE equalization

Active towers on one primary Grid share one cross-dimensional endpoint snapshot and one equalization transaction. Endpoints include tower coverage, manual and automatic bindings, loaded subordinate members, and Applied Flux networks.

The target is a common **capacity fill ratio**, not an equal FE amount:

- source-only endpoints supply first;
- sink-only endpoints receive only;
- ordinary bidirectional endpoints move only the amount above or below the equalization line;
- Applied Flux acts as a bidirectional buffer, fills real machine gaps, and absorbs ordinary source surplus;
- all extraction and insertion is frozen and simulated before execution;
- an already balanced state causes no real mutation;
- short writes compensate sources first, and uncompensated FE enters the tower quarantine buffer with an error log.

With Modern Industrialization installed, sided MI EU storage participates directly. Conversion uses the server's current `forgeEnergyPerEu`; an FE remainder smaller than one EU remains unmoved during preflight.

## Control interface

The header shows total capacity, physical usage, virtual leases, and remaining capacity. Each node can report “Allocated,” “Waiting for channel,” “Disabled,” “Waiting for target,” “Conflict,” or “Bridge error,” together with requested/granted channels, the failure reason, and frozen FE state.

- `Shift + Right-click` a target to disable or restore its transmission;
- middle-click a positioned target to highlight it and show coordinates;
- `Shift + Middle-click` a positioned target to teleport there as an administrator.

Logical nodes without coordinates are grouped at their binding anchor. They can be disabled individually but cannot be highlighted or teleported to.

## Range and power

The default coverage is a **1×1 chunk** centered on the tower. Every 16 Wireless Boosters add one horizontal ring:

| Wireless Boosters | Horizontal range |
| ---: | :--- |
| 0–15 | 1×1 chunks |
| 16–31 | 3×3 chunks |
| 32–47 | 5×5 chunks |
| 48–63 | 7×7 chunks |
| 64 | 9×9 chunks |

The vertical range reaches 128 blocks below and 256 blocks above the tower base, limited by world height. A default 1×1 range consumes **4 AE/t**; every additional chunk in the range adds **8 AE/t**.

## Troubleshooting

- A target is offline: check the target chunk, tower channel capacity, target type, and range.
- A point binding fails: confirm point-to-point mode, same dimension, range, and an AE or FE capability on the anchor.
- Channels are missing: inspect physical usage, Controller capacity, and virtual leases.
- FE does not move: check endpoint direction, fill ratios, Applied Flux state, and whether the target can receive.
