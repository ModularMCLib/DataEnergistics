# Adaptive Pattern Provider

An Adaptive Pattern Provider reads a compatible provider in its provider slot and inherits its name, icon, pattern-slot count, recipe categories, and registered special behavior. You do not need a separate block for every third-party provider.

## Blocks, parts, and upgrades

  <ItemImage id="data_energistics:adaptive_pattern_provider_part" scale="6" />

  <ItemImage id="data_energistics:adaptive_pattern_provider_upgrade" scale="6" />
  <RecipeFor id="data_energistics:adaptive_pattern_provider_upgrade" />
</Row>

- The block form can send ingredients in several directions and can host remote connector links.
- The part form mounts on a cable and primarily sends toward the side it faces.
- Both forms share inheritance, pagination, and upgrade rules, but **a part cannot be a remote connector host**.
- Hold the upgrade and right-click an ordinary AE2 Pattern Provider block or part to upgrade it in place while preserving patterns, names, and configuration.
- Each conversion consumes one upgrade item.

## Installing providers

Put a compatible provider in the provider slot. The interface then shows the inherited provider name and icon. The provider count directly affects the total pattern slots:

```text
total pattern slots = slots per provider × installed provider count
```

One stable provider item state should always resolve to the same name, icon, slot count, and capabilities. An unrecognized item is not silently treated as an ordinary provider.

## Capacity cards

<Row>
  <ItemLink id="ae2:capacity_card" />
  <ItemImage id="ae2:capacity_card" />
</Row>

The base accepts four providers. Each Capacity Card adds four more, up to three cards:

| Capacity cards | Maximum providers | Pattern slots with standard AE2 providers |
| ---: | ---: | ---: |
| 0 | 4 | 36 |
| 1 | 8 | 72 |
| 2 | 12 | 108 |
| 3 | 16 | 144 |

Before changing the provider type or removing a card, remove patterns above the new limit. The interface attempts to return overflow providers and patterns; an existing task continues on its original route.

## Redstone Tuning Card

<Row>
  <ItemLink id="data_energistics:redstone_tuning_card" />
  <ItemImage id="data_energistics:redstone_tuning_card" />
</Row>

With a Redstone Tuning Card installed, choose one of two modes:

- **Emit on dispatch**: emit a short pulse whenever a batch of ingredients is sent to a target;
- **Pulse-triggered request**: on each incoming pulse, request the primary output of every currently orderable pattern.

At very high dispatch speeds, adjacent devices may merge pulses. Use blocking mode or crafting locks when strict one-pulse sequencing is required.

## Targets and links

An Adaptive Pattern Provider can send to an adjacent target or use a [Distribution Connector](6.19_data_distribution_connector.md) to bind its block form to a loaded remote target in the same dimension.

- The connector host must be the full block form; provider parts are not supported as remote hosts.
- Each link stores a target position, target face, and link mode.
- `INPUT` sends ingredients, `PULL` retrieves target contents, and `BOTH` enables both directions.
- `Priority` starts with the earliest registered link; `Round Robin` continues from the last cursor.
- A remote link does not replace the target machine's native structure, power, light path, mana, or recipe requirements.
- Remote chunks must already be loaded; links never force-load them.

Use the connector page for key bindings, slot selection, copy/paste, and unlinking. See [Digital Packaged Pattern Provider](6.18_digital_packaged_pattern_provider.md) for real-machine dispatch requirements.

## Recipe categories and special capabilities

The adaptive provider only treats registered recipe categories and capabilities as supported. A provider's Mod namespace alone does not prove a special behavior, and a display name is never used as a compatibility test.

After a provider is installed, the recipe viewer matches the current recipe category and workstation item against the provider profile. A pattern is marked usable only when both sides match.

Registered capabilities may include special meteorite processing, advanced patterns, filtered input, mechanical crafting, and resonating behavior. Capabilities are composable, but an undeclared capability does not automatically add a button or dispatch route.

## Switching, removal, and recovery

- New orders use the currently selected route; materials, output, and sessions already accepted by the previous route must still finish or settle.
- Being temporarily offline, disconnected, or switched away is not proof that a route owns no assets. Drain old buffers before starting new background work.
- Removing a Capacity Card locks excess slots but does not silently delete existing configuration or tasks.
- Removing the host while a packaged task is active may create a recovery receipt. Restore the corresponding host at the original position and follow the packaged-provider recovery instructions.

## Troubleshooting

- The provider slot does not resolve: check that the item is a compatible provider, not only a similarly named block.
- A pattern cannot be ordered: check recipe category, workstation item, slot capacity, and the current capability profile.
- A remote target does not respond: confirm the full block form, same dimension, loaded chunk, target face, and target capability.
- Redstone pulses are merged: high dispatch rates can merge adjacent pulses; use crafting locks or blocking mode.
